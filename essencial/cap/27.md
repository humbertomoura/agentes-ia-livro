@CHAPTER CAPÍTULO 26|Projeto final: a padaria inteira|Ferramentas, memória, pasta, aprovação e trilha num só programa

Chegou a hora de juntar as peças. Neste capítulo, o atendente da Dona Cida ganha, num único programa, quase tudo o que construímos ao longo do livro. Ele consulta a agenda e registra encomendas sem duplicar, lembra da restrição da Dona Lurdes sem aceitar anotação perigosa, responde dúvidas citando a fonte (ou dizendo que não encontrou), recusa o que não tem permissão para fazer, para esperando a aprovação da Dona Cida quando o valor é alto e registra tudo numa trilha.

Antes de começar, um aviso honesto: este programa é um esqueleto didático, não o sistema pronto da padaria. O "modelo" é um conjunto de regras fixas, a memória vive num dicionário, a pasta tem dois trechos e nada é salvo em disco. Ele existe para mostrar, num lugar só, onde fica cada decisão. No fim do capítulo, dizemos o que falta para produção e como cada peça aparece num framework.

Como nos outros capítulos "Mão na massa", o código é Python puro, sem bibliotecas. Trocar o modelo simulado por um de verdade segue o caminho do capítulo 5.

## A trilha, a pasta e o caderno

Três peças de apoio. A `Trilha` é o trace do capítulo 21, bem simplificado: uma lista de spans. A `Pasta` é um RAG mínimo, com busca por palavras e a regra de só aceitar trechos com pelo menos duas palavras em comum com a pergunta; abaixo disso, ela devolve nada, e o agente diz que não encontrou. O `Caderno` é a memória do capítulo 9, com um portão de escrita que recusa números de cartão e anotações com cara de regra, e um portão de leitura que só devolve as notas da própria cliente.

@CODE
import hashlib
import json
import re

FINAIS = {"Sucesso", "Falha", "Limite atingido",
          "Bloqueado"}


class Trilha:
    """Um trace simples: uma lista de spans."""

    def __init__(self, conversa):
        self.conversa = conversa
        self.spans = []

    def span(self, tipo, **dados):
        self.spans.append({"tipo": tipo, **dados})


class Pasta:
    """RAG mínimo: busca por palavras com citação."""

    def __init__(self, trechos):
        self.trechos = trechos

    def buscar(self, pergunta):
        palavras = set(re.findall(r"\w+",
                                  pergunta.lower()))
        melhores = []
        for id_, texto in self.trechos.items():
            comuns = palavras & set(
                re.findall(r"\w+", texto.lower()))
            if len(comuns) >= 2:
                melhores.append((len(comuns), id_))
        melhores.sort(reverse=True)
        return [{"id": i, "texto": self.trechos[i]}
                for _, i in melhores[:2]]


class Caderno:
    """Memória com portões de escrita e leitura."""

    PROIBIDO = re.compile(
        r"\d{4} ?\d{4} ?\d{4} ?\d{4}|autoriz|desconto",
        re.I)

    def __init__(self):
        self.notas = {}

    def anotar(self, cliente, assunto, texto):
        if self.PROIBIDO.search(texto):
            return "recusado"
        self.notas[(cliente, assunto)] = texto
        return "anotado"

    def ler(self, cliente):
        return {a: t for (c, a), t in self.notas.items()
                if c == cliente}
@END

## O sistema e as ferramentas

O `Sistema` guarda a agenda, as encomendas, as cobranças, os estornos e as aprovações, e oferece as cinco ferramentas. Duas coisas merecem atenção. Cobrar e estornar são ferramentas diferentes: estorno não é uma cobrança com valor negativo, e tem regras próprias. E o método `encomenda` é a fonte oficial dos valores: uma cliente só enxerga as próprias encomendas, e a equipe do balcão enxerga todas. Repare que nenhuma delas recebe o nome da cliente como argumento: a cliente vem da sessão. `registrar_encomenda` e `gerar_pix` usam chaves de intenção, então um pedido repetido devolve o mesmo resultado.

@CODE
class Sistema:
    def __init__(self, pasta):
        self.pasta = pasta
        self.caderno = Caderno()
        self.agenda = {"sexta": 3, "sábado": 0}
        self.encomendas = {}
        self.por_numero = {}
        self.pix = {}
        self.estornos = {}
        self.aprovacoes = set()

    # ---- ferramentas (o que o modelo pode pedir) ----
    def consultar_agenda(self, sessao, dia):
        return {"dia": dia,
                "vagas": self.agenda.get(dia, 0)}

    def buscar_regra(self, sessao, pergunta):
        achados = self.pasta.buscar(pergunta)
        if not achados:
            return {"status": "não encontrei"}
        return {"evidencias": achados}

    def registrar_encomenda(self, sessao, bolo, dia,
                            valor):
        if self.agenda.get(dia, 0) <= 0:
            return {"erro": "dia lotado"}
        chave = f"{sessao['cliente']}:{bolo}:{dia}"
        if chave not in self.encomendas:
            self.agenda[dia] -= 1
            numero = f"E{len(self.encomendas) + 1}"
            registro = {"numero": numero,
                        "cliente": sessao["cliente"],
                        "valor": valor}
            self.encomendas[chave] = registro
            self.por_numero[numero] = registro
        return self.encomendas[chave]

    def encomenda(self, sessao, numero):
        """Fonte oficial do valor. Cliente só vê
        as próprias; a equipe vê todas."""
        enc = self.por_numero.get(numero)
        if enc is None:
            return None
        if (sessao.get("papel") != "equipe"
                and enc["cliente"] != sessao["cliente"]):
            return None
        return enc

    def gerar_pix(self, sessao, encomenda, valor):
        chave = f"pix:{encomenda}:{valor}"
        if chave not in self.pix:
            self.pix[chave] = f"PIX{len(self.pix) + 1}"
        return {"cobranca": self.pix[chave]}

    def solicitar_estorno(self, sessao, encomenda,
                          valor):
        chave = f"estorno:{encomenda}:{valor}"
        if chave not in self.estornos:
            numero = f"EST{len(self.estornos) + 1}"
            self.estornos[chave] = numero
        return {"estorno": self.estornos[chave]}
@END

## O executor e seus portões

O `REGISTRO` guarda o nível de risco e os campos de cada ferramenta. Repare no que `gerar_pix` e `solicitar_estorno` pedem: só o número da encomenda. O valor não vem do modelo. Quem calcula é `resolver`, buscando a encomenda no sistema e aplicando os 30% do sinal. É a regra do capítulo 6 levada a sério: dado oficial vem da fonte oficial, e o modelo diz apenas sobre o que agir.

A função `digital` gera a impressão digital da ação exata, como o `versao` do capítulo 13. A aprovação vale para aquela ação, com aquela encomenda e aquele valor. Se o valor mudar, a aprovação antiga não serve mais.

A função `executar` é o executor do capítulo 6, e as conferências acontecem numa ordem pensada:

- a ferramenta existe no registro?
- esta sessão pode usá-la?
- os campos recebidos são os esperados?
- os dados oficiais existem (a encomenda é real e é desta cliente)?
- o pedido faz sentido (um valor precisa ser positivo)?
- se é de risco alto, esta ação exata já foi aprovada?

O estorno, de risco R4, exige aprovação sempre; o Pix, de risco R3, só acima do limite. Só depois de tudo isso a ferramenta roda, e cada resultado vai para a trilha.

@CODE
# nome -> (risco, campos obrigatórios)
REGISTRO = {
    "consultar_agenda": ("R0", {"dia"}),
    "buscar_regra": ("R0", {"pergunta"}),
    "registrar_encomenda": ("R2",
                            {"bolo", "dia", "valor"}),
    "gerar_pix": ("R3", {"encomenda"}),
    "solicitar_estorno": ("R4", {"encomenda"}),
}
LIMITE_SEM_APROVACAO = 300


def resolver(sistema, sessao, nome, args):
    """Completa o pedido com os dados oficiais.
    O modelo diz qual encomenda; o valor vem
    do sistema, nunca do modelo."""
    if nome in ("gerar_pix", "solicitar_estorno"):
        enc = sistema.encomenda(sessao,
                                args["encomenda"])
        if enc is None:
            return None, "encomenda não encontrada"
        base = enc["valor"]
        valor = (round(base * 0.3, 2)
                 if nome == "gerar_pix" else base)
        return {"encomenda": enc["numero"],
                "valor": valor}, None
    return dict(args), None


def sentido(acao):
    """Validação semântica: o formulário certo
    ainda pode trazer um pedido sem sentido."""
    if "valor" in acao and not acao["valor"] > 0:
        return "valor precisa ser positivo"
    return None


def digital(nome, acao):
    """Impressão digital da ação exata."""
    texto = json.dumps({"acao": nome, **acao},
                       sort_keys=True)
    return hashlib.sha256(
        texto.encode()).hexdigest()[:10]


def precisa_aprovar(sistema, nome, acao):
    risco = REGISTRO[nome][0]
    alto = acao.get("valor", 0) > LIMITE_SEM_APROVACAO
    if risco == "R4" or (risco == "R3" and alto):
        return digital(nome, acao) not in \
            sistema.aprovacoes
    return False


def executar(sistema, sessao, pedido, trilha):
    nome = pedido["nome"]
    args = pedido["args"]
    if nome not in REGISTRO:
        resultado = {"erro": "ferramenta desconhecida"}
    elif nome not in sessao["permitidas"]:
        resultado = {"erro": "ferramenta não permitida"}
    elif set(args) != REGISTRO[nome][1]:
        resultado = {"erro": "campos inválidos"}
    else:
        acao, erro = resolver(sistema, sessao,
                              nome, args)
        if erro or sentido(acao):
            resultado = {"erro": erro or sentido(acao)}
        elif precisa_aprovar(sistema, nome, acao):
            resultado = {"bloqueado": "aprovação",
                         "chave": digital(nome, acao),
                         "valor": acao["valor"]}
        else:
            funcao = getattr(sistema, nome)
            resultado = funcao(sessao, **acao)
    trilha.span("ferramenta", nome=nome,
                resultado=resultado)
    return resultado
@END

## O controlador

`conversar` é o ciclo do capítulo 4. Ele abre a trilha, entrega ao modelo a mensagem e a memória da cliente, executa os pedidos e termina em Sucesso (o modelo respondeu sem pedir nada), Bloqueado (uma ação espera aprovação) ou Limite atingido (acabaram as voltas).

@CODE
def conversar(sistema, sessao, mensagem, modelo,
              max_voltas=5):
    trilha = Trilha(sessao["cliente"])
    trilha.span("mensagem", texto=mensagem)
    memoria = sistema.caderno.ler(sessao["cliente"])
    historico = [{"cliente": mensagem,
                  "memoria": memoria}]
    for volta in range(1, max_voltas + 1):
        pedidos, resposta = modelo(historico)
        trilha.span("modelo", volta=volta,
                    pedidos=[p["nome"] for p in pedidos])
        if not pedidos:
            return "Sucesso", resposta, trilha
        for pedido in pedidos:
            r = executar(sistema, sessao, pedido, trilha)
            historico.append({"pedido": pedido,
                              "resultado": r})
            if "bloqueado" in r:
                return "Bloqueado", r["bloqueado"], trilha
    return "Limite atingido", None, trilha
@END

## O modelo simulado

O "modelo" abaixo imita um LLM com regras fixas: pede a agenda e depois o registro quando a mensagem fala de bolo, pede um estorno quando a cliente fala em estorno, tenta gerar o Pix do sinal quando a mensagem fala de sinal e busca na pasta quando a mensagem é uma pergunta. Ele só extrai da mensagem o número da encomenda; quanto cobrar não é decisão dele.

@CODE
import re


def numero(msg):
    achado = re.search(r"\bE\d+\b", msg.upper())
    return achado.group(0) if achado else "E0"


def ultimo(historico, nome):
    for item in reversed(historico):
        pedido = item.get("pedido", {})
        if pedido.get("nome") == nome:
            return item["resultado"]
    return None


def modelo(historico):
    """Imita um LLM com regras fixas."""
    msg = historico[0]["cliente"].lower()
    memoria = historico[0]["memoria"]
    if "bolo" in msg:
        casamento = "casamento" in msg
        agenda = ultimo(historico, "consultar_agenda")
        if agenda is None:
            return [{"nome": "consultar_agenda",
                     "args": {"dia": "sexta"}}], None
        enc = ultimo(historico, "registrar_encomenda")
        if enc is None:
            return [{"nome": "registrar_encomenda",
                     "args": {
                         "bolo": ("casamento"
                                  if casamento
                                  else "cenoura"),
                         "dia": "sexta",
                         "valor": 1400 if casamento
                         else 90}}], None
        extra = ""
        if "restricao" in memoria:
            extra = f" ({memoria['restricao']})"
        return [], (f"Anotado: sexta{extra}, "
                    f"pedido {enc['numero']}.")
    if "estorno" in msg:
        feito = ultimo(historico, "solicitar_estorno")
        if feito is None:
            return [{"nome": "solicitar_estorno",
                     "args": {
                         "encomenda": numero(msg)}}], None
        return [], "Não posso. Chamo a Dona Cida."
    if "sinal" in msg:
        feito = ultimo(historico, "gerar_pix")
        if feito is None:
            return [{"nome": "gerar_pix",
                     "args": {
                         "encomenda": numero(msg)}}], None
        if "erro" in feito:
            return [], f"Não deu: {feito['erro']}."
        return [], f"Sinal gerado: {feito['cobranca']}."
    if "?" in msg:
        achado = ultimo(historico, "buscar_regra")
        if achado is None:
            return [{"nome": "buscar_regra",
                     "args": {"pergunta": msg}}], None
        if "evidencias" not in achado:
            return [], "Não encontrei essa informação."
        ev = achado["evidencias"][0]
        return [], f"{ev['texto']} [{ev['id']}]"
    return [], "Posso ajudar com encomendas."
@END

@BOX ANOTE AÍ|"Bloqueado" aqui quer dizer "nesta execução"
Quando o sinal de R$ 420 espera a aprovação, `conversar` devolve Bloqueado, com a chave daquela ação, e termina. Isso encerra aquela execução, não a tarefa: a encomenda continua existindo e segue quando a Dona Cida aprovar. Num sistema de verdade, o estado bloqueado fica salvo e a retomada parte dele, como no capítulo 13.
@END

@BOX PEGADINHA|A chave de intenção deste exemplo é simples demais
Aqui, a chave da encomenda junta cliente, bolo e dia. Se a Dona Lurdes quiser, de propósito, dois bolos de cenoura para a mesma sexta, o sistema acha que é o mesmo pedido repetido. Em produção, a chave precisa representar a intenção real do negócio: um número de pedido gerado quando a cliente confirma, por exemplo, e não uma dedução feita a partir de alguns campos.
@END

@BOX PEGADINHA|O portão do caderno é só uma ilustração
O portão de escrita procura números de cartão e as palavras "autoriz" e "desconto". Qualquer pessoa contorna isso com "a Cida liberou cortesia". Serve para mostrar onde o portão fica, não como ele deve ser. Portões reais combinam regras de formato, classificação do tipo de anotação e a regra do capítulo 9: nada que chega pela conversa vira política da casa.
@END

## Como isso ficaria num framework

Cada peça deste programa tem um equivalente nos frameworks do capítulo 25. Os nomes mudam de ferramenta para ferramenta, mas o papel é o mesmo.

@TABLE
Peça do projeto | Papel | Nos frameworks
`Trilha` | Registrar cada passo | Tracing, em geral com OpenTelemetry
`conversar` | Controlar o ciclo e os estados | Runner, grafo ou loop do agente
`Caderno` | Memória com portões | Memory store, com filtros próprios
`REGISTRO` e `executar` | Catálogo e portões das ferramentas | Tool registry, guardrails e middleware
`aprovacoes` | Esperar uma pessoa | Interrupções e human-in-the-loop
Estado entre execuções | Retomar depois de uma queda | Checkpoints de execução durável
@END

A diferença é que, no framework, você não escreve essas peças: configura. Por isso vale ter feito uma vez à mão. Você passa a saber o que procurar na documentação e o que conferir quando algo der errado.

## O que falta para a padaria de verdade

Este programa é pequeno de propósito. Para virar o sistema da padaria, faltariam as peças dos capítulos 12, 21 e 24: estado salvo em banco de dados e retomada depois de quedas, esperas com prazo, traces enviados a uma ferramenta de monitoramento, fila para os picos de sexta-feira, um conjunto de avaliação com os casos reais da padaria e, claro, um modelo de verdade no lugar do simulado. A estrutura, porém, é essa: o modelo propõe, e tudo o que importa é conferido pelo sistema.

@RESUMO
Ferramentas, memória, pasta, aprovação e trilha cabem num programa pequeno, sem framework.
A cliente vem da sessão; efeitos usam chave de intenção; memória e pasta têm portões.
O executor confere lista permitida, campos e aprovação antes de qualquer execução.
O controlador termina em Sucesso, Bloqueado ou Limite atingido, e a trilha registra cada passo.
O que falta para produção são as camadas dos capítulos 12, 21 e 24, não uma arquitetura diferente.
@END
